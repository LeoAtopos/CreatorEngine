# CreatorEngine 对话字段

使用本页维护对话状态、字段顺序与最低质量标准。每回合只处理一个字段；下列小节不是一次性问卷。

## 状态约定

每个字段记录为以下状态之一：

- `confirmed`：用户明确采用的文本；
- `blank`：用户选择暂留空；
- `pending`：尚未访问；
- `revisit`：用户要求稍后重做。

不要把助手提出但未经确认的候选写入报告。若用户直接给出新文本，将它视为候选，先检查是否适合句式，再确认。

## 0. 最初想法与工作名称

### `rawIdea` 最初想法

先请创作者用最原始、最感性的方式描述为什么想做这个游戏、脑中最先出现的画面/动作/关系或感受。原文必须保留，哪怕它模糊、不完整或互相矛盾。

检查：它是否表达了真实的创作火花，而不是被助手改写成营销文案。若只有类型名或空泛愿望，用一个窄问题追问“最让你兴奋的具体画面、行为或矛盾是什么？”

### `name` 工作名称

在理解最初想法后提出一个简短工作名；需要其他选择时，再给 2–3 个不同命名方向。工作名不需要承担所有设计信息。

## 1. 三句话之一：什么游戏

最终句式：

> 玩家作为___身份___，反复___核心动作___，以___目标___；但___约束或反转___。

按以下顺序逐项确认：

1. `gameplay.identity` 身份：玩家代入的主体视角。应能暗示能力、责任或处境，而不只是抽象标签。
2. `gameplay.verb` 核心动作：可重复、由玩家主动执行的动词短语。避免“体验故事”“感受世界”这类非交互表述。
3. `gameplay.goal` 目标：玩家想达成的结果，最好能够产生中间目标并说明行动意义。
4. `gameplay.constraint` 约束或反转：与身份、动作或目标形成张力的障碍、代价、限制或反转。仅写“敌人很强”通常不够具体。

段落复核：身份、动作、目标和约束是否能组成同一游戏循环；约束是否真正改变玩家做核心动作的方式。

## 2. 三句话之二：什么体验

最终句式：

> 为___目标玩家___提供___核心感受___，主要通过___关键动态___来实现，而不是依赖___常规方案___。

按以下顺序逐项确认：

1. `experience.audience` 目标玩家：用偏好、经验、容忍度或动机描述可做取舍的一群人，避免“所有玩家”。
2. `experience.feeling` 核心感受：玩家侧的体验价值，例如紧张、掌控、发现、依恋或释然；不要写功能或卖点清单。
3. `experience.dynamic` 关键动态：游玩过程中反复发生、能够生成该感受的行为—反馈—局势变化。
4. `experience.alternative` 常规方案：同方向作品通常依赖、而本作不准备主要依赖的做法。这一项也用于暴露竞品研究缺口。

段落复核：关键动态是否有合理因果路径产生核心感受；差异化是否改变体验，而不只是更换题材或美术皮肤。

## 3. 三句话之三：体验如何可行

最终句式：

> 如果让玩家___执行的机制___，那么他们会___产生的行为或策略___，进而感到___目标体验___；证据是___可观察信号___。

为了先固定验证目标，推荐按下列收集顺序；报告仍按上面的句式输出：

1. `hypothesis.experience` 目标体验：应与上一句核心感受一致或形成更精确的可验证版本。
2. `hypothesis.mechanism` 执行的机制：描述玩家实际观察、选择和执行的规则过程，而不是机制名称清单。
3. `hypothesis.behavior` 行为或策略：机制运行后，预计玩家会主动形成的模式、讨论、权衡或策略。
4. `hypothesis.signal` 可观察信号：试玩中可以看到、听到、记录或比较的行为证据；不要使用“玩家觉得很好玩”这类循环论证。

段落复核：机制 → 行为/策略 → 体验 → 信号是否是一条可被证伪的因果假设。

## 4. 四大设计支柱

按 `叙事 → 机制 → 美学 → 技术` 的顺序处理。每个支柱逐项确认基础框架、风格特点，再分别确认它对其他三个支柱的方向性指导、支持或要求。

### 支柱字段

- `tetrad.<pillar>.foundation` 基础框架：让团队知道它大致属于什么成熟类型、结构或实现范式。
- `tetrad.<pillar>.signature` 风格特点：说明这个项目在该支柱上可被感知的独特做法，而不是“优秀”“沉浸”等评价词。
- `tetrad.<pillar>.support.<target>`：源支柱对目标支柱提出的具体指导、支持或要求。它必须是有方向的设计关系，不是重复两个支柱的定义。

### 四个支柱的含义

- `narrative` 叙事：世界、主题、角色关系、信息结构、情节或玩家生成的故事。
- `mechanics` 机制：核心循环、规则、资源、挑战、反馈和玩家决策空间。
- `aesthetics` 美学：视觉、声音、界面、节奏、触感和整体呈现所形成的感知风格。
- `technology` 技术：平台、引擎、输入、联网、数据、性能、内容管线以及其他能力与硬约束。

### 每个支柱的内部顺序

以叙事为例，逐回合处理：

1. 叙事基础框架；
2. 叙事风格特点；
3. 叙事对机制的指导、支持或要求；
4. 叙事对美学的指导、支持或要求；
5. 叙事对技术的指导、支持或要求。

其余支柱使用同样的五项结构。不要把三个关系字段合并成一句含糊的“支持其他方面”。

支柱复核：至少一个支柱应足够鲜明，四个支柱不能完全缺席；检查双向关系是否相互支持、互不相关或直接冲突。

## 5. 玩家侧构思之一：接触游戏前

最终句式：

> 玩家看到游戏名称、介绍图，会认为这是一个关于___主题___的___类型___游戏，会和___关联游戏___关联比较，并产生___体验预期___的预期。

依次确认：

1. `player.firstLook.theme` 主题/题材：内容关于什么；名称和关键画面是否能传达它。
2. `player.firstLook.genre` 类型：玩家从机制和呈现上会归入的游戏类型。
3. `player.firstLook.references` 关联游戏：玩家很可能拿来比较的具体作品或清晰参照组。未知时标记为待研究，不要伪造调查结果。
4. `player.firstLook.expectation` 体验预期：只基于玩家进入游戏前能看到的信息，而不是创作者希望最终实现的全部体验。

## 6. 玩家侧构思之二：前 10 分钟

最终句式：

> 玩家在体验游戏 10 分钟内___会/不会___获得体验预期，___还能/而是___获得___独特体验___，玩家因此不会离开游戏，并产生___目标/期待___。

依次确认：

1. `player.firstTen.fulfilment`：选择“会”或“不会”，表示开场是否兑现游戏前预期。
2. `player.firstTen.outcome`：与上一项配成“会…还能…”或“不会…而是…”。若挑战预期，必须有足够强的新体验承接。
3. `player.firstTen.uniqueExperience`：前 10 分钟能够实际感知的独特体验，不是尚未出现的长期承诺。
4. `player.firstTen.nextGoal`：玩家在此后明确想继续追求、验证、收集、掌握或发现的目标/期待。

## 7. 玩家侧构思之三：中后期与终极体验

最终句式：

> 玩家中后期体验的变化来自___机制/内容___的出现，并最终在游戏结束时获得___游戏体验___的终极体验。

依次确认：

1. `player.arc.source` 机制/内容：使中后期体验发生主线变化的新规则、关系、内容结构、涌现、反转或长任务。
2. `player.arc.finale` 终极体验：在结尾才趋于完整、且能提升或重新解释核心体验的感受与意义。

最终复核：游戏前预期、前 10 分钟独特体验、核心感受和终极体验应形成有变化的同一体验弧，而不是四个互不相干的口号。
