# Markdown 报告格式

报告使用用户的语言；以下为中文标准。保持字段含义，不为了文采加入未经确认的设计。所有未确认字段写作 `（暂留空）`。

```markdown
# <游戏工作名称>

## 最初想法
<保留用户原文>

## 三句话

**一句话说明：什么游戏？**
玩家作为<身份>，反复<核心动作>，以<目标>；但<约束或反转>。

**一句话：什么体验**
为<目标玩家>提供<核心感受>，主要通过<关键动态>来实现，而不是依赖<常规方案>。

**一句话：体验如何可行？**
如果让玩家<执行的机制>，那么他们会<产生的行为或策略>，进而感到<目标体验>；证据是<可观察信号>。

## 游戏设计四大支柱

### 叙事
- 基础框架：<文本>
- 风格特点：<文本>
- 叙事对机制的指导、支持或要求：<文本>
- 叙事对美学的指导、支持或要求：<文本>
- 叙事对技术的指导、支持或要求：<文本>

### 机制
- 基础框架：<文本>
- 风格特点：<文本>
- 机制对叙事的指导、支持或要求：<文本>
- 机制对美学的指导、支持或要求：<文本>
- 机制对技术的指导、支持或要求：<文本>

### 美学
- 基础框架：<文本>
- 风格特点：<文本>
- 美学对叙事的指导、支持或要求：<文本>
- 美学对机制的指导、支持或要求：<文本>
- 美学对技术的指导、支持或要求：<文本>

### 技术
- 基础框架：<文本>
- 风格特点：<文本>
- 技术对叙事的指导、支持或要求：<文本>
- 技术对机制的指导、支持或要求：<文本>
- 技术对美学的指导、支持或要求：<文本>

## 玩家侧构思

### 第一句话：接触游戏前
玩家看到游戏名称、介绍图，会认为这是一个关于<主题>的<类型>游戏，会和<关联游戏>关联比较，并产生<体验预期>的预期。

### 第二句话：前 10 分钟
玩家在体验游戏 10 分钟内<会/不会>获得体验预期，<还能/而是>获得<独特体验>，玩家因此不会离开游戏，并产生<目标/期待>。

### 第三句话：中后期与终极体验
玩家中后期体验的变化来自<机制/内容>的出现，并最终在游戏结束时获得<游戏体验>的终极体验。

## 报告完整度
- 已确认：<数量或关键部分>
- 暂留空：<字段列表；没有则写“无”>
- 待研究或待验证：<明确列出>

## 设计问题诊断

### P0/P1/P2 · <问题标题>
- 类型：<已确认的矛盾 / 信息缺口 / 未验证假设>
- 证据：<引用或准确转述报告中的字段>
- 影响：<为什么会妨碍设计、体验或制作>
- 下一步：<一个具体决策、原型、调查或试玩观察>

## 优先下一步
1. <最重要的决策或验证>
2. <第二项>
3. <第三项>
```

## 输出规则

- 问题按影响排序，不按字段顺序堆砌。
- `P0` 表示会使核心概念无法成立或无法制作的冲突；`P1` 表示显著影响差异化、体验因果或玩家留存的风险；`P2` 表示可后续补充但需要记录的问题。
- 没有充分证据时，不使用 `P0`，也不把信息缺口写成已证实失败。
- 完整报告通常列出 3–7 个关键问题。报告很早导出时可以更少，重点标明空缺和下一步。
- 允许指出已有设计优势，但不要用优势冲淡问题诊断；优势只用于解释哪些部分值得保留。
- 不添加 CreatorEngine 的隐藏 JSON 元数据，除非调用方明确要求与网页应用往返兼容并提供相应数据结构。
